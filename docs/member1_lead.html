3Your Responsibilities — Detailed

3.1 — Before Coding (Day 1)

  • Create skillswap-backend and skillswap-frontend repos on GitHub
  • Invite M2 and M3 as collaborators on both repos
  • Protect main on both repos: require PR, require 1 approval, require up-to-date branch
  • Add .gitignore and README.md to both repos
  • Write docs/API.md v1.0 — the contract for auth + users endpoints (this is the single most important file in the project)
  • Create one shared GitHub Project board, link both repos
  • Add labels to both repos: backend, frontend, database, blocked, matching, urgent
  • Create Week-1 Issues on the board, assign owners
  • Post pinned Issue in each repo: branch naming (feature/xyz, fix/xyz, db/xyz), commit format (feat(scope): msg), PR template

3.3 — Code Review (Your Daily Job)

  • Review every backend PR — including M3's DB, chat, and session PRs
  • Review every frontend PR — M2 opens, you approve; M3's chat/session screens also need your approval
  • Review within 24 hours — this is your SLA. If you delay, the team blocks.
  • For each PR check: builds locally? matches API.md? no TODOs? commit messages follow convention? tests pass?
  • Only you click "Merge" on both repos

3.4 — API Contract Ownership

You are the only person who edits docs/API.md
  • Every new endpoint goes into API.md before anyone codes it
  • When you add an endpoint, post it in team chat same day
  • M3 may suggest endpoint snippets in PR descriptions — but you paste them into API.md
  • M2 consumes API.md exactly — never invents endpoints
If API.md changes without your approval, the frontend breaks silently. This is why you alone own the file.

3.6 — Friday Integration Day (Most Important Ritual)

  1. Pull both repos locally (git pull on backend and frontend)
  2. Start PostgreSQL, run backend (npm start), run Flutter on emulator
  3. Test the golden path: register → login → add skills → see match with score → send request → accept → schedule session → chat → mark complete → leave review
  4. For each bug: create an Issue in the correct repo (backend or frontend), assign owner
  5. Tag both repos with the same version: v0.1, v0.2, v0.3, v1.0 (Releases → Draft new release → tag)
  6. Update docs/API.md if contracts changed during the week
  7. Post a summary in team chat

4What You Do NOT Do

  • NEVER Write frontend Flutter code — M2 owns it
  • NEVER Write database/schema.sql or migrations — M3 owns them
  • NEVER Write chat.service.js or session.service.js — M3 owns them
  • NEVER Let someone else merge to main
  • NEVER Push directly to main — always via PR
  • NEVER Let a PR sit unreviewed for more than 24 hours
  • NEVER Skip Friday Integration Day

5Your Daily Workflow

Every time you push a zip from your series
  1. Extract zip → open HOW_TO_PUSH.md
  2. Run the git commands in order: git checkout -b feature/xyz → git add (per logical change) → git commit -m "feat(scope): msg" → git push
  3. Open PR on GitHub: title from HOW_TO_PUSH.md, base main, label backend
  4. Self-review (or ask M2 to review)
  5. Merge
  6. Delete the branch
  7. git checkout main && git pull
  8. Open the next zip

6How Your Success Is Measured

✅ main always runs — no broken commits
✅ All PRs reviewed within 24 hours
✅ API.md kept in sync with code
✅ Golden path passes every Friday
✅ Both repos tagged same version weekly
✅ Demo ready on Week 4
Your job is 70% coordination, 30% coding. If you code 100% of the time and skip reviews/board/integration, the project will fail — even if your code is perfect.
