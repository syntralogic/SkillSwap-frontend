3.3 — API Contract Discipline (Most Important Rule)

You NEVER invent endpoints. If a screen needs data and the endpoint isn't in API.md, you:
  1. Do not code against a guessed URL
  2. Open an Issue on the skillswap-backend repo titled "Endpoint needed: GET /xyz"
  3. Tag M1 in the Issue
  4. Wait for M1 to add it to API.md
  5. Then code against the real endpoint
Your API client (lib/services/api_service.dart) rules
  • Every method name maps to an API.md endpoint (e.g. login() → POST /auth/login)
  • Every method returns a typed model (User, Profile, Skill, Match, Request, etc.)
  • JWT stored in flutter_secure_storage or shared_preferences
  • JWT attached automatically to every protected request via interceptor
  • On 401 → clear token → navigate to login
  • On network error → return a typed error, don't crash the screen

3.4 — UI/UX Standards

  • Every screen has: loading state, empty state, error state, success state
  • Every form uses validators.dart — no inline validation logic
  • Compatibility score is shown visually (badge, progress bar, color) — the matching screen is the app's hero feature
  • No hardcoded strings for API URLs — all in api_service.dart
  • Responsive: test on at least 2 screen sizes (small phone + tablet)

3.5 — Push Workflow (Every Zip)

Every time you push a zip
  1. Extract zip → open HOW_TO_PUSH.md
  2. Run the git commands in order: git checkout -b feature/xyz → git add (per logical change) → git commit -m "feat(scope): msg" → git push
  3. Open PR on GitHub: title from HOW_TO_PUSH.md, base main, reviewer M1, label frontend
  4. Wait for M1's approval — do not merge yourself
  5. After M1 merges: git checkout main && git pull, delete the branch
  6. Open the next zip
