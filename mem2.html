3.3 — Database Discipline

Database rules
  • All 11 tables from SRS — Users, Skills, Categories, User_Skills, Availability, Exchange_Requests, Sessions, Messages, Reviews, Notifications, Reports
  • Every table has a primary key (id or <table>_id)
  • Every foreign key declared with REFERENCES and ON DELETE behavior
  • Indexes on foreign keys and frequently queried columns (user_id, status, skill_id)
  • Migrations are idempotent: CREATE TABLE IF NOT EXISTS — so re-running is safe
  • Seed users password = demo123, hashed with bcrypt (same salt cost as M1's backend)
  • Seed creates at least 3 mutual matches so the matching algorithm demo works immediately
Never break the schema between zip 1 and zip 2. Migrations 002–005 must be pure additive changes (CREATE TABLE, ALTER TABLE ADD COLUMN) — never drop or rename columns M1's code already uses.

3.7 — Push Workflow (Every Zip)

Every time you push a zip
  1. Extract zip → open HOW_TO_PUSH.md
  2. Check which repo the branch belongs to (backend or frontend) — HOW_TO_PUSH.md tells you
  3. cd into the correct local repo
  4. Run git commands: git checkout -b <branch> → git add → git commit -m "feat(scope): msg" → git push
  5. Open PR: title from HOW_TO_PUSH.md, base main, reviewer M1, label backend or database or frontend
  6. Wait for M1's approval — do not merge yourself
  7. After merge: git checkout main && git pull, delete branch
  8. Open the next zip
